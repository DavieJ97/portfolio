04 / Featured case study

TeachersOnline:
From Desktop Application to Web Platform

TeachersOnline began as a desktop application intended to make interactive educational games easier for teachers to use. As I considered how teachers install, access, and share classroom tools, I saw friction in the desktop delivery model. I adapted the project into a browser-based platform. The journey reflects an iterative way of building: identify a problem, create an initial solution, learn from its limits, and reshape the architecture around its users.

EDTECH PLATFORMEvolving project

Built around a teacher’s workflow.

The goal is to make interactive games and practical lesson resources easier to reach, prepare, and use in class—without turning the technology itself into another task for the teacher.

Python · FlaskJavaScript · CSSSupabasePython DOCX generation

01 / The problem

Keep the lesson moving.

PowerPoint game templates can be a convenient starting point. In some implementations, though, adapting or maintaining them can take extra effort: complex animations and interactions may break, and keeping score can fall to the teacher.

01 · PREPARATION

Manual setup

Editing a template for a new class or activity can add preparation work.

02 · RELIABILITY

Fragile interactions

When a complex animation or interaction stops behaving as expected, the teacher has to troubleshoot during the lesson.

03 · CLASSROOM FLOW

Scoring by hand

Manual scorekeeping can pull attention away from facilitating the activity.

These were the challenges that motivated my project, not a claim about every teacher or every presentation.

02 / First implementation

A desktop app built while learning.

I started with an installable application built in Python, PyQt6, and Pygame, with the aim of making interactive educational games easier to use. Building it pushed me to teach myself object-oriented programming: how to use classes and functions, and how to organize an application into reusable parts.

That first version was a useful way to explore the problem and grow my programming skills. As I thought more about how the intended users would access and share the tools, the friction around installation and distribution became hard to ignore.

WHAT IT TAUGHT ME

Python fundamentals, classes, functions, and reusable application structure.

WHAT IT SET OUT TO DO

Give teachers a dedicated desktop way to use interactive educational games.

03 / Reconsidering delivery

The application worked toward the goal; installation added friction.

The desktop version was a valuable first step, but the delivery model asked teachers to install an app, manage updates, and find it on whichever computer they were using. Sharing it and its resources with another teacher also meant passing around an application. For this audience, a browser-based experience offered a simpler route in.

↓

Installation

A hurdle for users who may not install desktop software often.

↻

Updates

New versions can require another download or update step.

▣

Different computers

The app may not be installed on each classroom computer.

↗

Sharing

A website is easier to send to another teacher than an installer.

04 / Rebuilding for the web

The browser became the front door.

I taught myself JavaScript and CSS and moved the project to Flask. Teachers can open the games in a compatible browser; I can update the platform centrally, and Python can continue handling work that fits the server better.

01 · CLIENT

Teacher’s browser

HTML and CSS present the tools. JavaScript handles in-game interactions and game state in modules such as battleship.js and classroom_pirates.js.

JavaScript · CSS
02 · APPLICATION

Flask + Python

Flask serves pages and routes. Python handles worksheet and answer-key generation as Word documents, and provides the translation endpoint used by the worksheet editor.

Flask · python-docx
03 · DATA & AUTH

Supabase

The app uses Supabase Auth for sign-up, login, and password recovery, and reads or updates profile and preference records in its PostgreSQL database.

Supabase Auth · PostgreSQL

REQUEST / RESPONSE FLOW

Browser interaction runs in JavaScript. Worksheet export is sent to Flask, which builds the documents in memory and returns them as a ZIP download.

Browser→Flask→DOCX + ZIP

05 / Beyond games

A broader teaching toolkit.

The web version grew beyond the original game concept into a set of classroom resources.

Browser-based classroom games

The current code includes review games such as Battleship and Exploding Kittens, alongside the speaking game Classroom Pirates. Their interactive mechanics live in browser-side JavaScript.

Client-side game logic

Worksheet builder and Word export

Teachers can assemble unscramble, fill-in-the-blank, translation, and word-search sections. Python section classes build the worksheet and answer key; Flask returns both as a ZIP of Word documents.

Server-side Python

Translation support

The worksheet editor calls a Flask endpoint, which uses the deep-translator package and Google Translator to request a translation.

Flask endpoint

06 / Engineering lessons

What the transition taught me.

Architecture follows the user

Installation and sharing friction made browser access a better fit for teachers than preserving a desktop-only delivery path.

Learn the tools the problem needs

Moving from PyQt6 and Pygame to Flask, JavaScript, and CSS meant learning new technologies to keep the product moving.

Put work in the right place

Interactive game state belongs in the browser; generating Word worksheets and answer keys is a good fit for Python on the server.

Keep adapting the first idea

The first implementation helped me start. Reviewing how it fit classroom workflows gave me a reason to change the delivery model.
